# 核心机制

行为层：引擎保证什么、节点出口如何被校验、执行如何隔离，以及如何在同一引擎上跑自定义工作流。逐步用法见[使用](USAGE-zh.md)，安装见[安装](INSTALLATION-zh.md)。

## 行为契约

- **文件即真相。** 状态机存放在单个文件（`.flow-comet/flow-comet-state.json`）中，只能由守卫的出口命令推进。引擎需要知道的关于这项工作的全部信息，都能从 `.specs/` 下的工件推导出来；进度不存在对话里，任何会话只要重新读取工件就能接着做。
- **门禁，不是建议。** 从节点推进是一次被校验的转移：守卫检查该节点的工件、结构、已记录的节点证据，以及工作流要求的各项声明。
- **默认 fail-closed。** 当某个判定无法被证明是安全的——协议文件读不出来、状态或载荷解析失败、工作流状态未知、某条路径无法被证明留在项目内——引擎选择拒绝而不是继续。只有明确空闲的状态（没有 change，或 change 已完成）才被视为不受约束。
- **边界必须声明。** 任何形似"用户授权"的动作——接受超过上限的修复轮次、重入已归档的 change、由协调者接管任务——都必须是显式且被记录的声明。引擎把沉默当作拒绝。

### 安装清理

对已有副本重装时，也会清掉该副本不该再持有的内容：在安装器管理的、平台技能树下的技能目录内，当前技能包已不再包含的路径会被删除——改名或移走的页面因此不会留在安装副本里。清理按位置判定，且 fail-closed：这些目录之外一概不看，目录之内凡是无法证明归它管理的一律保留并打印原因——自身是链接或解析后落在项目之外的受管理目录、符号链接、与权威源同路径但类型不同的条目、以及清完残留后仍非空的目录。清理先于任何复制，因此清理完不成时，安装会在复制开始之前停下；读不出来的路径不会被当成不存在；每一次删除与每一次保留都会打印；重复运行不再删除任何东西。

安装器管理的范围就是当前技能包本身，因此不再属于它的整个技能目录永远不会被进入——手工自建的目录与「技能已被移除」的目录，从外面无从区分。这种情形交给显式重置（`--purge`）处置，而不是靠猜。

重置（`--purge`，需第二次确认）是更宽的工具，其作用范围不限于执行它的那个项目。它会删除所选平台的项目侧生成物并重建——而对 DeepSeek Harness 来说，删除还会延伸得更远，触及两处全局挂载：`$DSH_HOME/plugins/` 下的桥接 loader 与 `$DSH_HOME/cordis.patch.yml` 里安装器的托管块。这两处属于 harness 家目录，而不属于任何项目，却是每个 profile、每个已通过该平台安装的项目用来拦截写入的东西：在一个项目里跑重置，会把这份共用面从所有项目上摘掉，然后在同一条命令里重建。

三个细节决定这件事是否要紧。重建会把执行这次命令的那份副本的版本写进共用 loader，因此版本不同的项目会在自己的健康检查里报出这个差异；重建之前就被打断的运行，会让共用面一直处于摘除状态，直到从任意项目再跑一次该平台的安装；而只有该平台在所选重置范围内时，共用面才会被动到——重置另一个平台只落在项目自身范围内。因此重置的正确用法是丢弃项目自己的生成物——它既是处置「安装器无法证明归它管理的技能目录」的指定手段，也是卸载某平台的手段——而不是「卸载一个项目、让其它项目照常工作」的办法，也不是一个例行步骤。

### 技能文本分层

分发的册子遵循一条「内容该放哪一层」的规则。它决定你是在手头这册里读到某段内容，还是被指去别处读。

| 内容 | 归属 |
|---|---|
| 节点自己的作业指导——该节点的步骤、领域方法，以及该节点特有的坑 | 节点册正文 |
| 多个节点都要用的纪律或事实 | 一处权威，加上每个需要的册子里那句「何时去读」的话 |
| 引擎已经持有的东西——产出 schema、门禁、命令、证据字段 | 向引擎现问，而不是抄进册子 |
| 维护者自己的叙事——订正、日期、已作废的结论 | 移出分发面 |

第二行是干活时会遇到的那一类：共用的纪律不会在每册各写一遍，每册带着的是那句条件句——句子点名权威文件，并说明在什么情况下打开它。没有任何册子指向的共用文件按「读不到」处理，因此共用文件会与通往它们的那些句子对账。在入口册之外的任何册子里，指针写成指向入口册 `reference/` 目录的显式路径，而不是裸相对路径——裸形态按写在哪册就按哪册解析，从节点册写出来指不到任何地方。第三行是册子可以让你去问引擎、而不必印出节点要求的原因；那条命令见[守卫校验](#守卫校验)。

这条规则取代了早先「同一段文字要在多册出现」的规则，检查方向也随之反转：需要这段内容的每册都必须带那句指针句，权威必须被点名为唯一来源，正文不得出现第二份。这项检查有三点属于约定本身，而不属于它的实现方式。指针句被排除在正文比较之外，因为持有它正是设计对每册的要求——把它算进去，要么让合规的册子判红，要么什么也判不出来。「出现第二份」的门槛按对从两侧中较短的那份正文派生，而不是事先定死：定死的门槛一度高于实际存在的正文长度，一处真实重复就这么一路判绿，直到门槛改为派生才现形。比较只覆盖文字仍逐字相同的那些对；已经漂移的一对没有可比的共同正文，因此不在它之内——这是已知缺口，留给后续处理。

## 三条防线

| 防线 | 做什么 | 在哪执行 |
|---|---|---|
| ① 物理写入拦截 | 工具写入之前，平台 hook 按当前节点的写入白名单检查目标；越界写入在平台层就被拒绝 | 安装器写入平台的 `PreToolUse` hook |
| ② 守卫校验 | 节点的进入与出口按证据校验：必需工件与段、已记录的节点证据、技能加载声明、任务集签名、完成任务的摘要、审查处置标记，以及 `verify` 真实执行的测试命令 | 守卫的 `entry` / `exit` |
| ③ 状态与 schema 校验 | 每次状态写盘都按 schema 校验（字段类型、嵌套记录），不可写的形态被拒绝而不是被静默规范化 | 状态机的写盘路径 |

同一套纪律也给了协调者一条被强制执行的边界：默认执行模式下，协调会话不得亲自执行实现任务（引擎会报告越俎代庖）。实现工作委托给子代理，必须回传可核验的契约——提交、验证的真实输出、以及它声明完成的检查项。并行委派的安全来自一份四属性契约——写权限、提交隔离、验证隔离、集成纪律；独立工作树只是「写权限」的一种实现，不是契约本身，共享工作区同样是受支持的形态。

**Hook 的阻塞语义与边界。** hook 以退出码 2 加原因输出来阻塞一次写入；在平台的交互式会话里这就是一次拒绝。有两条平台级前置值得知道——缺失时 hook **无法**拒绝，尽管机制本身完好：

- Claude Code 通过它能找到的 shell 执行 hook；若宿主发现不了 Bash（例如 Windows 上的 Git Bash），hook 会落到一个跑不起来安装形态命令、且非零退出不被当作阻塞的 shell。把 POSIX shell 的路径告诉平台即可恢复阻塞。
- Codex 只在 hook 信任已被接受（交互式 `/hooks`）时执行项目 hook，或由脚本化运行传入平台的旁路开关。两者都没有时，hook 根本不会执行。

这两条都是宿主前置而非引擎行为；满足前置后，真实会话会拒绝越界写入，并在节点允许后放行同一写入。

## 守卫校验

每个节点上，守卫回答一组固定的问题；任何一个"否"都会带着原因与修复命令拒绝放行：

| 问题 | 适用节点 |
|---|---|
| 进入是否已记录，节点的技能加载声明是否存在？ | 所有节点 |
| 节点的文档是否存在、首部字段与段名是否符合模板？ | `open`、`design`、`plan`、`execute`、`subagent-execute`、`review`、`verify`、`archive`——每个节点只按它自己产出的工件判（见下表） |
| 任务是否全部完成、每个完成任务是否有摘要、任务集是否未被改动？ | `execute`、`subagent-execute` |
| 自检是否已声明，降级的那一种是否带证据？ | `execute`、`subagent-execute`（SUMMARY 的自检段） |
| 验证是否真的跑过、是否通过？ | `verify`（执行 `TEST.md` 的命令块） |
| 审查的每条发现是否都有处置、被转待办的 Major 是否有用户裁决？ | `review` |
| 归档目录与其遗留清单是否就位？ | `archive` |

模板形态这一问按**工件**逐个答，而不是按节点答——有的工件由两个节点共同产出，有的节点一次产出两份：

| 节点 | 被校验形态的文档 |
|---|---|
| `open` | `CHANGE.md`、`REQUIREMENT.md`，以及项目级的 `CONTEXT.md`（存在才查） |
| `design` | `DESIGN.md`；前端 change 另要求 `UI-DESIGN.md` 在场，其形态也按模板校验（存在才查） |
| `plan` | `TASK.md`，外加每个任务块必须带齐的七个字段 |
| `execute`、`subagent-execute` | 每份 `<任务号>-SUMMARY.md` |
| `review` | `REVIEW.md` |
| `verify` | `TEST.md`；`UAT.md` 没有上游模板，只查存在性 |
| `archive` | 无——它的遗留清单同样没有上游模板，因此只查存在性 |

模板决定的是骨架，模板表达不了的东西来自随技能树一起装的登记表：哪些段是条件段、哪些子段是结构子段、本仓在上游之外追加了哪些段，以及报错文案里引用的标题形态与首部键名。由此有四条边界：条件段必须保留标题、正文写 `N/A` 即可；标注为可选的段允许整段删除；父段「适用」时其结构子段必须在场，父段整段 `N/A` 时子段不要求。你在模板之外自加的段不参与校验，而不是被拒绝。模板（或登记表）缺席时，受影响的工件报「未校验」而不是「通过」——内置兜底骨架被有意取消，因为那只是同一份骨架的第二份副本。

这些出口上的任何不符都会打印 `BLOCKED`，并给出模板路径与按类别的计数；具体段名只在同一工件再次失败时列出。`archive` 不在这条链路里：它的遗留清单没有可比的骨架。

因为校验是结构性的，"看起来像契约但解析不出来"的载荷与"文件缺失"会被同样拒绝——引擎从不猜。

节点的自检按**声明**校验，不评判质量：摘要必须写明六维审查是怎么跑的——引擎可用时走引擎、加载不到时手读引擎的协议文件、最后才用内置快查——且内置形态还须写明引擎不可用的原因与替读的证据。这条声明在**两处**分别校验，且互不替代：「自检方法」段必须写明方法名，「六维自查」段也必须带上方法名——即便方法段已声明内置快查，六维自查段仍须出现 `brooks-review` 或 `cache-brooks`；这正是排障页从另一侧写明的同一条要求。引擎只校验措辞；审查本身的质量仍由 review 阶段把关。

节点的要求也可以现问，不必去节点册里翻：`workflow-state.mjs explain <node>` 会打印该节点的输出 schema 及其产物路径与证据 id、它的 guardrails 表、它要求加载的技能、它把关的 `TEMPLATE:` 模板路径（零模板节点没有这一行），以及 entry / exit / record 三条命令——命令按本安装实际运行的形态给出。每一行都派生自引擎本已读取的协议，因此答案不会与门禁实际执行的内容分叉。该命令只读——不写状态、不改路由——节点名非法即拒绝，并列出全部合法取值。

### 模板快照与指纹

登记表锁定它派生自的那套模板：`templateCommit` 记上游提交，每份模板记其文本按与骨架同一口径归一后的 sha256——去 BOM、把 CRLF 与 CR 折成 LF，因此行尾差异不改变指纹。这份快照在模板能被取到的地方校验：quality 作业按登记表点名的上游提交检出同一份快照，用门禁所用的同一骨架模块逐模板重算，任何一处不一致、任何派生不出骨架的模板、以及登记表提交与安装器锁定点不符，都会让作业判红。要移动这份快照，就得在同一次改动里连登记表和安装器的锁定点一起更新。

运行期，指纹是提示而不是门禁。守卫只读项目 `flow-kit/` 检出的 `HEAD`——不起 git 子进程、不写任何东西——发现提交与登记表不符时打印 `TEMPLATE-FINGERPRINT WARN`，随后仍按登记表快照校验骨架；这行每个项目根在一个进程里最多打印一次，从不阻断节点。未提交的模板字节改动也不会触发它：逐模板哈希只在快照在场的 quality 作业里比对，而不是在每次出口上比对。

### 归档提名核对

归档出口读取提名记录，而不是相信一句摘要：`lessonsNomination` 写明扫描了多少份任务摘要、提名了哪些条目，以及没有提名时为什么。扫描份数必须等于该 change 实际持有的 `*-SUMMARY.md` 份数（无论出口时它的目录还在活动目录，还是已经移入归档目录）；每个被提名的编号都必须在 `LESSONS.md` 里真实存在；提名清单为空时必须给出非空理由。任何一条不成立都会被拒绝，并附上替换这份证据的 `record` 命令。

这项校验与其它校验一样是结构性的：它证明读过了、编号是真的，不证明被提名的条目值得保留——那是审查阶段的判断。在规则生效之前创建的 change 只告警，不阻断。

### 加载一个节点

进入节点时，门禁跑之前先给出两条指针，顺序固定：`READ PROMPT:` 指向 `flow-kit/prompts/` 下的协议提示词——**步骤权威**，这一步怎么做；`READ TEMPLATE:` 指向 `flow-kit/templates/` 下的模板——**段形权威**，产出长什么样。顺序本身即语义：先步骤，后段形。没有上游模板的节点（`verify`、`archive`）只打印提示词行，没有随包提示词的节点只打印模板行。两行都不会给出不存在的路径，也不依赖协调者记得交代。`design` 节点在前端 change 上还会多打印一行条件提示词（`READ PROMPT: 2a-ui-design.md`），判据与条件模板行同源；非前端 change 不打印，`CHANGE` 模板缺失、判据无依据时同样不打印。

两条指针同时在加载该节点技能时声明，声明因此能与产物对照审计：`--prompt` 必须是该节点自己的协议文件之一，声明到别处的路径会在下一次入口被拒绝，并附上重新声明要跑的命令；`--templates` 必须与该节点的模板集合完全一致——缺失、多写或错名在新的 change 上被拒绝、旧 change 只告警；零模板节点省略该参数；自定义协议节点按协议自己声明的 `templates` 走。声明记录的是「要求你读了什么」，真正读没读仍由产物门禁证明。

### 上游协议的覆盖声明

上面点名的两套权威——提示词管步骤、模板管段形——可能分歧。当上游提示词自己的段号或段表与模板不一致时，本仓不会默默照任何一边执行：分歧以声明的方式写明——在入口册，以及在覆盖面更窄的节点册——逐项列出哪些上游文件是只读基准、哪些上游表述不采用、哪些沿用，以及多处声明并存时以哪一处为准。

覆盖是声明，不是改动：`flow-kit/prompts/` 与 `flow-kit/templates/` 下的 vendored 文件保持只读，因此每一处分歧都能对着未被改动的上游审计。拒绝越序推进的阶段门是工件门的加强，而不是替代——工件仍是唯一真相，阶段门只是把「缺工件」从很晚才发现提前到出口直接拒绝。

## 执行模型

工作以 change 为单位推进：工件在 `.specs/<change-id>/`，项目是 git 仓库时每个 change 一个分支（`change/<change-id>`），一次只走一个节点。实现工作按那份四属性契约委托给子代理，并由它们交回契约证据；默认模式下协调者不得写源码。审查之后需要修复的 change，要经执行节点的生命周期回到流程，而不是就地打补丁——这样修复与原工作受同一套出口门禁约束。

### 并行委派

守卫按身份判定，不按路径判定：宿主把调用方标成子代理时，子代理语义在解析任何路径之前生效，约束协调会话的那份写入白名单不再决定结果。最小保护集——状态文件与协议文件——对子代理仍然拦截，因为手改它们正是破坏状态的来源。

| 平台 | 委托形态 | 工作区（谁建树） | 写权限通道 |
|---|---|---|---|
| Claude Code | `Agent` 工具 | harness 可建独立树，也可由子代理共享工作区 | 载荷 `agent_id` / `agent_type`——**证实**，且**限定形态**：Windows + Claude Code v2.1.177 + `permission_mode = bypassPermissions` + 一次性仓库载体；`agent_type` 取值域、嵌套委派载荷、非 Windows 环境**仍未覆盖** |
| dsh | 平台进程内子代理 | 不建树——子代理共享工作区 | 桥接透传的身份深度 + 通道标记——**证实** |
| Codex | 原生多代理会话 | 共享工作区，或由协调者显式建树 | 载荷 `agent_id`——交互式会话**已证实** |

判级逐行给出并保持不变：未覆盖项不写成已支持。三平台剩下的唯一差异是"谁建树"。共享工作区形态下，边界来自互不重叠的任务写集、提交时点纪律与最小保护集。

## 恢复

状态始终可重新推导：`status` 打印机器视图，`next` 打印当前节点与继续命令，`advance` 在状态确实错位时强制推进，`select <change-id>` 切换 change。拒绝出口的节点会打印原因；修法永远是补上消息里点名的那样东西——首次给模板路径与按类别的计数，再犯才点出段名——绝不手工编辑状态文件。

## 侧命令

有三条命令随技能树一起装好，但都在 8 节点流程之外：`evolve`、`health` 与 `context-scan`。它们作用于整个项目，而不是某一个 change，因此不参与路由、不经过任何节点的进入或出口门禁，也不记录节点证据。它们也不会被自动触发：由你显式调用。`evolve` 在写入前要求你逐项批准候选；`health` 在你调用时写入报告；`context-scan` 在你调用时写入报告和扫描元数据。

| 命令 | 什么时候用 | 留下什么 |
|---|---|---|
| `evolve` | 归档 change 里积累的架构沉淀该过一遍，折回项目自己的文档 | `.specs/evolve/<YYYY-MM-DD>-EVOLVE.md` 报告，以及为你逐项批准的候选所改动的项目文档 |
| `health` | 想在决定做什么之前，定期看一眼代码库与它的技术债 | `.specs/health/<YYYY-MM-DD>-HEALTH.md` 报告；报告里的发现只是建议，是否立成工作另做决定 |
| `context-scan` | 项目上下文文档该重新探测，并与上次扫描做比对 | `.specs/context-scan/<YYYY-MM-DD>-SCAN.md` 里的快照与差异清单 |

装了代码体检工具时，其四维结果并入同一份报告并标注来源；不在场时报告保留显式降级声明。可选工具缺席不会让该命令失败。

两条边界值得记住。侧命令绝不推进工作流：它不记录任何进展，也不能顶替节点的工件，所以永远不是绕过门禁的捷径。它同样只报告、不替你决定：`evolve` 只写入你逐项批准的内容，`health` 把每条发现留给你处置，三者都不会替你开 change。上次架构沉淀过期时，状态视图会补一行提醒——那只是建议，本身不执行任何命令。

再有一条侧命令是协议组合器，见下方[自定义协议](#自定义协议)；入口与各平台的命令路径见[使用](USAGE-zh.md)。

## 自定义协议

`/flow-comet-compose` 是侧命令（不在 8 节点链上），引导你把任意已安装技能组合成一个 JSON 形式的自定义工作流协议。此后该协议由同一引擎驱动——状态路由、守卫校验、hook 拦截——不需要任何新的运行时能力。内置的 8 节点协议仍是默认工作流，且不会被替换。

**协议加载优先级**：命令行 `--protocol <path>`（或 `--protocol=<path>`）> 环境变量 `FLOW_COMET_PROTOCOL`（在平台的项目环境里设置即持久）> 内置默认。不显式指定时，一切行为与内置协议完全一致。

**最小结构**：协议声明 `schemaVersion`（`1`）、`kind`、`name`、`nodes[]`、`outputSchemas[]`，可选 `writeWhitelist` 与 `taskFile`。每个节点写明实现它的技能（`implementation.skill`）以及它必须满足的输出 schema。

**让它真正可用的规则**：

1. **每个节点都要有工件** —— 被引用的 schema 必须在 `outputSchemas[]` 中存在且工件路径非空；没有工件就没有可校验、可恢复的东西。
2. **每个节点都要有证据** —— 每个 schema 携带其证据 id，这正是 `record` 写入、出口检查的东西。
3. **节点 id 必须避开内置八个** —— `open`、`design`、`plan`、`execute`、`subagent-execute`、`review`、`verify`、`archive` 为保留 id。
4. **写入边界要声明** —— 协议可自带白名单（节点 id → 允许的路径前缀，支持 `<change-id>` 占位符，使一个协议服务所有 change）。省略时：内置 id 沿用内置表，自定义 id 默认使用协调者白名单——允许写 `.specs/` 下，写其它位置需要显式声明。
