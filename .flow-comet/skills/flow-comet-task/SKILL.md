# flow-kit TASK Protocol

本 Skill 为 flow-comet 的 plan 节点提供 flow-kit 的 TASK 拆解流程。

> **模板权威**：本节点产出工件的段形 = **上游模板 + 本仓登记的增量段**——唯一权威 = `flow-kit/templates/**`（段与正文），条件段 / 结构子段 / 增量段与指纹由 `../flow-comet/reference/artifact-templates.json` 登记；`.specs/archive/**` 是历史证据、**不是模板来源**——不得以「上一轮就是这么写的」对齐段形。

## 加载

读取 `flow-kit/prompts/3-task.md` 并按其执行。关键步骤：

1. **Artifact Preflight**：检查 REQUIREMENT.md + DESIGN.md 存在
2. **拆解原则**：
   - 大小：fresh context 2~10 分钟可完成
   - 粒度：按文件冲突切（垂直切片），不按层切
   - 并行标记 `[P]`：只给本波确有并发同伴、且 write_files 互不重叠的任务；孤立任务一律串行——「互不冲突」只是必要条件，不等于应标 `[P]`
   - **同一文件 ⇒ 同一任务**：一个文件只能有一个任务 owner；必须拆分时，在波次划分中显式排序并写明拆分理由与依赖方向，不得把同一文件的两处改动拆成无依赖的两个任务
   - **[P] × direct 模式**：`[P]` 任务只在 `subagent-execute` 节点委托消化；direct 模式只放行串行任务的主代理直写，`parallel="true"` 任务在 direct 下仍必须委托——direct 不是并行任务的逃生口；共享工作区以 `write_files` 互斥 + 提交时点（提交前 diff 边界）作为相互隔离纪律
   - **四属性可满足（并行安全契约）**：标 `[P]` 的任务须确认**并行安全四属性**（① 写权限 · ② 提交隔离 · ③ 验证隔离 · ④ 集成纪律）可满足——worktree 只是「① 写权限」的实现之一，不是前提；四属性的**含义与三平台通道**以入口册「并行委派契约（四属性）· 三平台通道」为单一来源，本册只点名不复述
   - 波次形态：依赖驱动多趟语义——每个并行任务显式声明 `depends_on`（后波依赖前波任务），引擎按依赖拓扑自动分趟消化（每趟委托全部依赖已满足的并行任务，趟间回串行），混排序列（串→并→串／并→串→并等交错形态）合法，无需压扁成单一串行段；硬性拦截（规划出口 BLOCKED，附恢复指引）：任务块结构（至少一个 `<task>` 块）/ 每任务 `<verify>` 字段 / 新格式任务的 7 字段在场（集合见第 3 条；缺任一即 BLOCKED——7 字段一项在旧式一字段模板形态下仅 WARN）/ 任务图依赖环 / 缺失依赖（`depends_on` 引用不存在的任务 id）/ 并行写写冲突（并行任务 `write_files` 重叠）——任一项不成立即被拦（读写重叠仅 WARN），修正后重新 exit 即可通过；跳过未满足依赖先跑并行同样被拦。落笔时先画依赖方向再标 [P]。flow-kit 上游模板未载此约束，以本条为准
   - **波次 = 依赖层级的投影（波次编号的判据）**：每个任务的波次 = 其依赖中最晚波次的下一波（无依赖 = 第 1 波）；同波任务必须彼此没有依赖；想让某任务晚一点跑，就写 `depends_on` 把顺序声明出来，而不是把它挪到后面的波却不声明。声明波次与依赖层级不一致（同波依赖 / 排在依赖之前 / 明明只需更早波次却排得更靠后）→ 在 plan 出口 **BLOCKED**，明细逐条点名「任务 / 依赖 / 当前波 / 应到波」并给两条恢复出路：把该任务移到第 N 波，或补 `depends_on` 把顺序声明出来。判不了按成因二分——载体缺席（`## 波次划分` 不在 / 段名无从派生）→ 出口打印「未校验（无波次段）」并跳过该判据（未验证 ≠ 通过）；内容不可判（段在场而没有一行 Wave 行能落到真实任务 id）→ 出口打印 `TASK.md 波次划分段内容不可判`，一律 BLOCKED（同一形态一个判级）。另：TASK 里的每个非修复族任务都必须被某个 Wave 行覆盖——修复族不要求排进波次，漏写的任务在明细里以「未声明」的当前波被点名。`replan` 重校走同一判据、同一报文。本条只要求「波次编号与依赖层级一致」，与上面的混排合法化并存——不恢复旧的「并行块必须连续成组」形态约束
   - 依赖：`depends_on: <task-id>`
3. **每任务 7 字段**：name / read_files / write_files / action / verify / done / depends_on——与 plan 出口「新格式任务的 7 字段在场」判据同一集合；`id` **不是字段**，它是 `<task>` 元素的属性（`<task id="T01" parallel="true" status="pending">`）；`depends_on` 元素必在（无依赖写空元素）
   - **write_files 必须包含关联测试文件**：若任务修改组件/函数，且有关联测试直接 import 其本地导出（如 `src/**/__tests__/*.test.ts` 从组件文件 import），该测试文件**必须纳入该任务 write_files**。否则组件删除本地导出/改 import 后，关联测试会编译失败或断言失效（实测：改组件时破坏了关联测试文件）。
4. **波次划分**：跨层顺序；同层任务只有确有并发同伴、且 write_files 互不重叠时才标 [P]，孤立任务一律串行；**波次编号是依赖层级的投影**——层 = 1 + 依赖中最晚层（无依赖 = 第 1 波），写出「无依赖 / 第 N 波」的对应关系，不要用挪动波次代替依赖声明（判据与恢复指引见第 2 条同名条目）；flow-kit 上游宽松语义（「无冲突即可标 [P]」「同层即同波并行」）以本节点为准（显式覆盖，vendored 只读不改）
5. **XML 格式**：便于 AI 解析与执行

## 产物

- `.specs/<change-id>/TASK.md`（XML 格式任务列表 + 波次划分图）

## 状态推进

本 Skill 满足 `flowkit.plan.v1` Output Schema。TASK.md 完成后由 flow-comet 状态机推进到 execute 阶段。
并行任务由 subagent-execute 节点按依赖分趟委托执行——委托节点可多次往返，直至无依赖已满足的可并行 pending 且无串行残留。
