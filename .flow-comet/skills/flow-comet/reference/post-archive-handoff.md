# 归档完成后的交接（Known-Issue 后续处理）

> **读者对象**：刚把一个 change 归档完、要处置本批遗留清单的执行者（agent）与协调者。
> **何时读**：`exit archive --apply` 通过之后、要决定本批遗留项进什么载体时读；入口判定、探测、展示与确认、降级与失败的处置也都在本页。
>
> 本页只写协议与判据：没有脚本、没有新命令、不读写工作流状态。文中示例一律用通用占位（如 `some user report`），不带任何具体项目的过程编号与路径。

## 触发与顺序

**步骤权威**在 `../flow-comet-archive/SKILL.md` 的「归档完成后的交接」段（触发时机与八步顺序）；本页写操作矩阵与细则，两处不一致时以归档册为准。

**触发点**：`exit archive --apply` 通过、状态进入 completed 之后。归档的出口判定不因本步骤改变——交接成功、跳过或失败，都不影响「归档已完成」这个事实，也不回写任何归档结论。

**顺序（固定，不重排）**：

1. 归档出口通过（脚本打印 `NEXT: done`）。
2. 只读地看当前分支名与工作区状态——**仅用于随后的报告与提交前展示**，不据此推断默认分支、不据此决定动作。
3. 读本次归档目录下的遗留清单 `KNOWN-ISSUES.md`（只读，不改写、不回填）。
4. 跑一次只读探测（见「探测（只读）」）。
5. 做一次载体询问（见「一次载体询问」）。
6. 把选中载体将创建 / 写入的内容**完整展示**，由用户选粒度并确认（见「展示、粒度与确认」）。
7. 按选择执行，逐条报告结果。
8. 只有本地写入才进提交子流程（见「提交（仅本地写入）」）。

**本步骤不做任何分支操作**：不 merge、不 checkout、不 rebase、不删除分支、不 push。归档册的分支收尾（项目启用分支模式时的独立收尾动作）与本步骤无关；本步骤只读分支名用于展示。

## 入口条件

| 条件 | 处理 |
|---|---|
| 工作流状态缺失或为 completed | 允许（归档后即处于该状态） |
| 状态为运行中（还有在办的 change） | 拒绝：提示先完成并归档当前 change；不探测、不写盘 |
| 状态文件损坏 / 不可解析 | 拒绝（fail-closed）：报错并指向恢复指引；不猜测、不重建 |
| 归档目录不存在 | 报错：给出期望路径 |
| 遗留清单 `KNOWN-ISSUES.md` 不存在 | 报错：给出期望路径 |
| 清单为空 / 明确写「无遗留问题」 | 报告「本批无遗留项，无需交接」；**不提问、不写盘** |
| 条目解析失败（个别） | 跳过该条并可见；报告列出跳过项 |
| 条目全部解析失败 | 停止并报错；不提问 |
| 事后补做（不是紧接归档） | 列出最近的归档目录让用户选；不自动挑 |

入口判定全部通过之前不探测、不展示、不写盘——判定失败时给出的信息必须能让用户直接修（哪个文件、缺什么）。

## 探测（只读）

固定命令块，逐条执行；命令只读，不写盘、不改状态、不写入凭证（`auth status` 只读，用来判断认证状态）：

```bash
# 1) 是否位于 git 工作树内（非 git 项目据此走降级）
git rev-parse --is-inside-work-tree

# 2) remote 分类：github.com / gitlab.com / 自建 host / 无 remote
git remote get-url origin

# 3) 对应 CLI 是否在场（Windows 用 where，其他平台用 which 或 command -v）
where gh
where glab
which gh
which glab

# 4) CLI 版本（在场才查）
gh --version
glab --version

# 5) 认证状态（按 host 逐个查，不自建判定）
gh auth status --hostname <host>
glab auth status --hostname <host>
```

| 探测项 | 结果形态 | 影响 |
|---|---|---|
| git | 是 / 否 | 否 → 无提交；公开载体只给命令 |
| remote | github.com / gitlab.com / 自建 / 无 | 推荐哪个载体、用哪个 CLI |
| CLI 在场 | gh 在场 / glab 在场 / 都不在 / 都在 | 推荐与降级形态 |
| CLI 认证 | 已认证 / 未认证 / 未知（认证 = 该 host 的登录状态通过，即 `gh auth status` / `glab auth status` 退出码为零） | 能否直接创建 issue |
| 本地 roadmap | 无 / 符合规定形式 / 有但不符 / 不可解析 / 多份 | 追加 / 问一次重建 / 迁移 |
| 分支与工作区 | 当前分支名、`git status --short` | 只进报告与提交前展示 |
| 探测命令失败 | 标「未知」 | 显式降级，不猜、不假定 |

**「未知」标记**：命令不存在、退出码非零、输出不可解析时，一律记「未知」，并把该格按最保守的降级处理；不得把「未知」写成「不在场」或「已认证」。

探测摘要（remote 分类 + 各 CLI 在场 / 认证 / 本地 roadmap 形态）原样带进下一节的提问，让用户在提问里就能看到依据。

## 一次载体询问

**每批只问一次**：这批遗留项进什么载体。**范围只限载体本身**——后面的粒度选择、是否提交、是否转入，都是各自独立的确认，不算对这一问的「追问」。

| 选项 | 说明 |
|---|---|
| GitHub Issues | 用 `gh` 按目标项目现有 issue 模板创建 |
| GitLab Issues | 用 `glab` 创建 |
| 本地 roadmap | 写进项目自己的路线图文件（索引 + 每条一份文件） |
| 暂不处理 | 结束本步骤，不写盘；不记忆，下一次归档仍会问 |

规则（缺一不可）：

- **问题里带探测摘要与推荐**：remote 分类、哪些 CLI 在场 / 已认证、本地 roadmap 形态；推荐按右侧矩阵给，给理由。
- **不逐项询问**：载体是一批一个决定。
- **不缓存**：不把选择写进任何状态文件或记忆字段；下一次归档重新问。
- **不可用的选项仍然列出**：标注「将给你内容与命令」（CLI 不在场 / 未认证 / 无 remote 时），不要因为降级而把选项藏起来。
- **用户取消**：停止；不写盘。
- **是交互会话才提问**：平台有结构化提问工具就用它（不同平台的工具名不同）；没有该工具时退回文本提问 + 内联确认。
- **非交互会话**：不提问；打印探测摘要 + 四个选项 + 「本步骤需要交互会话」后**停下**，把它报告为一个未决决策点；不写盘、不替用户选择。

| remote | 对应 CLI | 本地 roadmap | 推荐 |
|---|---|---|---|
| github.com | gh 在场且已认证 | 任意 | GitHub Issues |
| gitlab.com | glab 在场且已认证 | 任意 | GitLab Issues |
| 自建 host | 任一 CLI 在场且已认证 | 任意 | 该 CLI（问题里注明 host） |
| 任意 | 不在场 / 未认证 | 有 | 本地 roadmap（追加） |
| 任意 | 不在场 / 未认证 | 无 | 本地 roadmap（新建）或暂不处理 |
| 无 remote / 非 git | 任意 | 任意 | 本地 roadmap |
| 自建 host | 两个 CLI 都在 | 任意 | 两个选项都列，由用户选 |

## 展示、粒度与确认

**展示不截断**：选中公开载体后，先展示将要创建的全部内容——每条的标题、建议类型、正文要点。内容多时分批展示（标注「第 n 部分，共 m 部分」），**分批不等于省略**；用户没看全就不进入确认。

**粒度由用户选**（看完具体清单之后问一次）：

| 粒度 | 结果 |
|---|---|
| 逐条 | 每条遗留项一个 issue（可分别指派 / 关闭） |
| 汇总 | 整批一个 issue，正文按条目分组列全部内容 |
| 自选 | 先选条目子集，再对子集选「逐条 / 汇总」 |
| 取消 | 不创建；报告「已取消」 |

**确认**：用户显式选择条目并确认后才执行创建 / 写入。外部创建不可逆，**未经确认不创建、不写盘**。汇总形态下若本批类型混合，汇总 issue 的类型也由用户选。

**执行前查重**：创建前按标题查远端是否已存在（`gh issue list --search "<标题关键词>" --state all` / `glab issue list --search "<标题关键词>"`）；已存在的跳过并在报告里点名。远端搜索索引可能有延迟，漏判是已知边界，失败时不静默。

**本地 roadmap 转入（仅选了公开载体且本地 roadmap 存在且可解析时问一次）**：是否把本地路线图里的条目转入公开载体——全部 / 选一部分 / 不转，**默认不转**。转入的条目与本批合并展示（同样分批不截断、同样选粒度）。不删除、不改写本地 roadmap，也不自动回填双向对应关系。本地 roadmap 不可解析时不提供转入，只处理本批。

## issue 类型与标签

| 类型 | 标题前缀 | 标签 | 何时用 |
|---|---|---|---|
| bug | `[bug]: ` | bug | 可复现的缺陷 / 回归 |
| enhancement | `[feature]: ` | enhancement | 新能力 / 改进 |
| documentation | `docs: ` | documentation | 文档 / 说明性工作 |
| task | `[task]: ` | task | 其他已确认要做的具体工作 |
| 待定 | — | — | 判断不了：展示清单时标「待定」，让用户选 |

规则：

- **以前缀与标签对齐目标项目的现有模板**：创建前读目标项目的 issue 模板，取它的 title 行与 labels 行；模板给出的映射优先于上表。
- **判断不了不要默认成 task**：标「待定」，在展示清单时逐条让用户选；类型是公开面的一部分，猜错会误导维护者。
- **标签缺失不算失败**：目标项目没有对应标签时，无标签重试并在报告里告警；标题前缀仍按映射。
- **没有对应模板的类型**（例如项目没有 documentation 模板与标签）：用本节的最小正文骨架 + 无标签重试并告警，不要因此拒绝创建。
- **本地 roadmap 没有标签概念**：类型只用于公开 issue；本地条目用「状态 / 优先级」等索引列表达。

## 公开草稿的写法

判据不是「通过词表」，而是**维护者能读**：草稿要写成一份可以直接接手处理的 issue，而不是一段过程记录。

**先纳入目标模板的必勾项**：目标项目的 issue 模板若有必勾项（至少「公开内容确认」——正文不含过程代号或未公开内容），先满足这些必勾项，再按下面的骨架填正文。

**七段主线（缺陷类）**：

1. 用户版本：什么版本 / 什么安装方式。
2. 终端：平台 + 关键输出，原文粘贴。
3. 现象：用户实际看到什么。
4. 复现：从干净状态开始的最小步骤。
5. 期望：应该发生什么。
6. 代码位置：文件与函数；定位不到就写「未定位」。
7. 未验证：哪些部分没有验证、为什么——写清楚，不要用「应无影响」含糊过去。

**其他类型的最小骨架**：

- enhancement：动机（当前痛点）/ 目标（想要什么）/ 验收（怎样算完成）。
- documentation：写什么 / 为什么 / 在哪（哪份文档或哪一节）。
- task：目标 / 范围 / 验收 / 关联（可空）。

**删掉过程词**：跑次与重跑次数、某个提交的测试组、验证 / 归档 / 基线 / 正控 / 留档 / 测试强化提交这类过程叙述，一律不进入对外正文；它们回答的是「我们做过什么」，维护者要的是「用户遇到什么、怎么复现、期望什么、改哪里」。

**维护者第一遍读**：写完由作者以「第一次读这个仓库的人」的身份复读一遍——只有正文、没有会议上下文时能否看懂？需要额外背景才能理解的段落，就是还没写好。

**机械词表 0 命中不等于通过**：词表只能拦固定词，拦不住过程视角；0 命中之后仍可能读起来像过程记录。两件事都要做：词表自查 + 第一遍读。

**示例用通用占位**：如 `some user report`、`<文件>:<行>`；不写具体项目的过程编号、编号化的工作项、不公开的路径。

## 本地 roadmap

**规定形式**：项目根（或项目内任一目录）的 `ROADMAP.md` 作为索引 + 每条一份 `<ID>.md`。

- 索引七列：ID / 标题 / 状态 / 优先级 / 时间向 / 负责人 / 链接。
- 每条六段：What / Why / Context / Acceptance / Links / Notes。
- 反膨胀：只列活跃项、一行一条、设上限（如五十条，超出告警）、完成即移出；不建附录、证据区、历史堆叠。
- 条目编号：`KI-<change-id>-<序号>`（只在本项目内使用）。

**探测**：按文件名找 `ROADMAP.md`（不区分大小写；含维护者文档目录；跳过 `.git` / `node_modules` / 归档目录）。命中多份时列出让用户选用哪份，另一份不动。

**判定三分**：

- **符合规定形式** → 追加索引行 + 条目文件；不改写既有条目、不重排序。
- **不符合但有结构可解析**（表格 / 列表 / 分段散文）→ 问一次：① 按本形式重建（推荐）② 另建旁路清单 ③ 只建 issue ④ 用户自己处理后重跑。不静默改写。
- **不可解析** → 同上一档；重建映射由用户逐段指定。

**重建四要素**（缺一不可）：

1. 完整展示原文（分批不截断）。
2. 同目录备份 `<name>.bak-<UTC>`：文件名可见、不以 `.md` 结尾（避免被当成新文档）、不自动提交。
3. 逐段映射表：每段映射到一个条目或「显式丢弃」，一次确认、可改；有段落无法归类就停下问用户，不静默丢内容。
4. 重写：只重写被重建的那份；其余文件不动。

**失败即停**：备份失败、映射无法完成、写入失败 → 原文件保持不动（有备份则备份保留），报告原因，不给出「差不多好了」的结论。

**结构锚（目标文件本身被机检锚定时）**：若被重建的路线图是项目用机检锚定的维护文档（例如带固定段落与表头新鲜度），重建必须保留其结构锚；保留不了就停下问用户，不要为了重建而拆掉机检锚点。

**新建**：先问位置（推荐 `docs/roadmap/`，另可选 `.specs/roadmap/`、项目根 `roadmap/`，必须在项目内）与是否入 git；**未选择前不落盘**。选了私有（不入 git）时：先 `git check-ignore`；已忽略 → 报告现有规则；未忽略 → 展示 diff 后追加一个带注释的忽略块，幂等，且该改动不自动提交（否则只在本机生效这件事要明说）。

## 提交（仅本地写入）

只有本地写入（本地 roadmap 条目、被忽略的忽略块、旁路清单）才涉及提交；创建 issue 不走 git。

1. `git check-ignore -v <写入路径>`
   - **被忽略** → 不提交、**也不提问**（没有可提交的内容）；报告命中的规则并提示：忽略块本身要用户自己提交才会对他人生效。
   - **未被忽略** → 展示将提交的路径 + 当前分支 → **问一次「是否提交」**。
2. 用户确认后按 pathspec 提交：

```bash
git add -- <写入路径>
git commit -m "chore: record known-issue handoff" -- <同一组写入路径>
```

3. 用户不提交 → 留在工作区并报告；不追问第二次。
4. 提交失败（hook 拦截 / 分支保护 / 并发锁）→ 报告原始输出，文件保留，可重试；**不 push、不 merge、不切分支**。

**pathspec 纪律**：只提交本次写入的路径，且一律追加新提交——五要素全文见 `reference/commit-discipline.md`（当本趟有多个写者共享同一工作区、要按 pathspec 提交时读它）。**不假设默认分支名**——main / dev / master 都是别的项目的约定，本步骤只展示、不推断。

## 降级与失败

| 情况 | 处理 |
|---|---|
| 对应 CLI 不在场 | 完整展示标题与正文 + 可直接执行的 `gh issue create` / `glab issue create` 命令；`glab` 命令带 `--yes`；**不声明已创建** |
| CLI 在场但未认证 | 同上，附 `gh auth status` / `glab auth status` 的失败原因，让用户认证后可自行执行 |
| 无 remote | 命令带 `-R <owner>/<repo>` 占位；本地 roadmap 仍可用 |
| 非 git 项目 | 公开载体只给命令模板；本地 roadmap 无「入 git」选项、无提交 |
| 自建 host | 先问用哪个 CLI，再按对应行处理 |
| 提问工具不可用 / 非交互会话 | 不提问：打印探测摘要 + 四个选项 + 「本步骤需要交互会话」；不写盘、不替用户选 |
| 探测失败 | 标「未知」，按最保守路径降级；不猜 |
| 创建部分失败 | 立即停止；报告已创建与失败清单（含原始错误），未创建的给出命令；重跑按标题去重只补未创建的 |
| 标题已存在 | 跳过并点名；不算失败 |
| 标签不存在 | 无标签重试 + 告警；标题前缀照旧 |
| 标题 / 正文超限 | 不静默截断；提示缩短或拆分后重来 |
| 写入 / 备份失败 | 报告原因；原文件保持不动，备份保留；停止 |
| 归档已完成态 | 交接的任何失败都不回写归档结论、不把归档判成未完成 |

降级输出的形态固定为「内容 + 命令」两件套：内容让用户能直接复制成 issue，命令让用户有一条可执行的路。降级不是失败——但**降级不得伪造成成功**：没创建就写「未创建」，不要写「已创建（降级）」。

## 边界

- **不写状态文件**：不写 `.flow-comet/flow-comet-state.json`、不新增任何字段、不把载体选择缓存成记忆——下一次归档照样重新问。
- **不回填历史**：只处理本次 change 的遗留清单；不读取、不导入、不修改、不提示历史归档里的清单（读目标项目自己的本地 roadmap 是允许的，那不叫历史回填）。

- **不自动关闭**：不关闭 issue、不做 PR 关联、不做逐项分诊（一批一个载体决定）。

- **不改机制**：不改协议文件、不改归档出口判定、不改 hook 判定；本步骤对引擎是只读的。
- **不截断展示**：任何情况下都不以「内容太长」为由省略待创建 / 待写入的内容。
